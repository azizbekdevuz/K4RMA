# K4RMA 협업 규칙

작업 전에 읽고 적용한다. 현재 파일 배치는 [STRUCTURE.MD](STRUCTURE.MD), AI 진입점은 루트 [AGENTS.md](../AGENTS.md)다.

## 1. 작업 범위와 승인

- 요청·대화·브랜치로 담당과 승인 범위를 확인한다. 시작 시 `git status --short`, `git diff`로 기존 변경을 구분하고 타인의 작업을 덮어쓰지 않는다.
- 기본 작업 범위는 2절의 담당 경로다. 그 밖의 코드·공통 아트·Resources·씬·프리팹·설정·패키지·공통 검사·도구·문서는 공통 파일이다. 담당 보스의 전용 도구는 `tools/<보스명>/`에 둔다.
- **공통 파일을 추가·수정·이동·삭제해야 하면, 먼저 대상·이유·변경 내용·영향받는 보스를 설명하고 사용자 승인을 받는다. 승인 전에는 변경하지 않는다.** 보스 수정 요청, 필요성 판단, 사전 공유만으로 승인받은 것으로 간주하지 않는다. 이미지 공용화·문서 갱신·공통 실행기 변경도 같은 기준을 적용한다.
- 예외: `tests/` 아래의 검사 파일은 공통 검사를 포함해 작업에 필요한 추가·수정·이동·삭제를 별도 승인 없이 진행한다. 보스별 검사 배치·기대값 소유권은 2절을 따른다. 이 예외는 `tests/` 밖의 게임 코드·에셋·설정·문서·실행 도구 변경에는 적용하지 않는다.
- 사용자가 이미 명시적으로 승인한 대상과 범위는 재승인 없이 구현·검증·정리까지 진행한다. 범위가 추가되거나 승인 여부가 불명확하면 해당 변경을 보류하고 질문한다. 도구의 권한 승인은 별도다.
- 자신의 임시 생성물 정리는 6절에 따라 진행한다. 이를 공통 소스·에셋 변경의 승인으로 확대하지 않는다.

## 2. 보스별 담당과 구조

경로는 저장소 루트 기준이며, 새 파일도 담당 폴더에 둔다.

| 담당 | 코드 | 아트·효과·재질·셰이더 | 검사 |
|---|---|---|---|
| RisingSlash · 상승베기 | `Assets/Scripts/RisingSlash/` | `Assets/Arts/Resources/RisingSlash/` | `tests/Unity/RisingSlash/` |
| SwordWave · 검기 | `Assets/Scripts/SwordWave/` | `Assets/Arts/Resources/SwordWave/` | `tests/Unity/SwordWave/` |
| Guard · 방어 | `Assets/Scripts/Guard/` | `Assets/Arts/Resources/Guard/` | `tests/Unity/Guard/` |

- 보스의 공격·선택·이동·방어·피격·자세·효과·수치와 검사 기대값은 그 보스의 담당 폴더에서 수정한다. 다른 보스의 구체 타입·전용 상태·전용 애니메이션 메서드를 참조하지 않는다. `partial`은 공통 호스트 접근 수단이며 다른 보스 상태 접근 허가가 아니다.
- `Behavior`는 공격 목록(`BuildCycle`)·선택(`Eligible`)·이동(`TickMovement`)·공격 주기·연결을 담당한다. 검기 이동은 `KarmaSwordBossMovement.cs`, 개별 공격은 `Patterns/`, 전용 연출은 `Visuals/`, 방어 기본 공격은 `Patterns/GDBasic.cs`다.
- 공통 호스트는 `BossBehavior`의 피해 경계·피격 효과·접촉 결과·방어·공격 종료·카메라·패링 입력 계약을 호출한다. 보스는 자기 파일의 `[BossKind]`로 등록하고 설정 접근은 `KarmaBossTuning.*.cs`에 둔다. 공통 팩토리에 보스별 분기를 추가하지 않는다.
- 기존 `EnemyAttack` 숫자는 호환성을 위해 유지한다. 새 전용 패턴은 보스 폴더에서 이름 있는 `const EnemyAttack` 캐스트 상수로 선언한다. 확장 ID는 SwordWave=1000~1999, RisingSlash=2000~2999, Guard=3000~3999이며 공통 enum에 추가하지 않는다. 공격 목록·해금·기대값은 담당 Behavior와 소유권 검사에서 갱신한다.

### 공통 모듈 의존성

- `Core`의 규칙·기하 계산은 Unity 오브젝트·UI·보스 구체 타입에 의존하지 않는다. `Game`의 설정 코드는 저장 에셋에서 런타임 복사본을 만들고, 같은 모듈의 게임 흐름 코드가 플레이어·전투·월드의 수명을 조정한다.
- 보스 패턴은 공통 전투·플레이어 계약을 호출한다. 공통 호스트는 `BossBehavior`의 가상 계약으로 보스별 정책을 조회하며 보스 구체 타입을 역참조하지 않는다. 연출은 상태를 읽고 표시하며 피해 판정이나 저장 상태를 소유하지 않는다.
- 별도 코루틴·풀·캐시를 소유하는 컴포넌트는 해당 기능 파일에 두고 중단·비활성화·재진입 시 정리한다. 새 추상화는 실제 결합이나 중복을 줄일 때만 추가한다. 직렬화 필드·GUID·공개 논리 키는 구조 정리만을 이유로 바꾸지 않는다.
- 입력 설정은 기존 `K4RMA.InputBindings.v1` JSON을 유지한다. 런타임 맵의 GUID가 바뀌면 저장된 `K4RMA/<동작명>`과 기존 UI의 첫 바인딩 계약으로 복원하며, 문서 전체 검증 전에 활성 키를 교체하거나 손상된 저장값을 덮어쓰지 않는다.

## 3. 설정·이미지·애니메이션·VFX

### 수치

- 저장 수치는 `Assets/Data/Resources/Karma…BossProfile.asset`에서 수정한다. 접두사는 RisingSlash=`KarmaRising`, SwordWave=`KarmaSword`, Guard=`KarmaGuard`다.
- Inspector의 `settings`가 실제 저장값이다. `Karma…BossSettings.cs` 초기값만 바꿔서는 기존 에셋에 반영되지 않는다. 피해·이동·판단·회복 배율은 Profile의 `damageScale`·`movementScale`·`decisionScale`·`recoveryScale`을 사용한다. 런타임은 복사본이므로 수정 후 Play Mode를 다시 시작한다.

### 배치와 연결

- `Assets` 바로 아래에 `Arts`(이미지·애니메이션·재질·셰이더), `Audio`(소리·카탈로그), `Scripts`(코드), `Data`(게임·렌더링 설정), `Scenes`(씬)를 둔다. 새 중간 프로젝트 폴더나 별도의 `Art` 폴더를 만들지 않는다.
- 아트는 `Arts/Resources/<소유자 또는 화면>/`에 둔다. 소유자는 `Player`, `Guard`, `RisingSlash`, `SwordWave`, `Neutral`이며, 배경·튜토리얼·UI는 `Backgrounds`, `Tutorial`, `UI`, 여러 기능이 함께 쓰는 원본은 `Shared`에 둔다. 오디오는 `Audio/<기능>/`에서 별도로 관리한다.
- 코드는 `Scripts/<기능>/`에 둔다. `Game`은 초기화·진행·입력·설정, `Combat`은 공통 전투 계약과 적 호스트, `Presentation`은 공통 연출을 담당한다. 전용 에디터 코드는 해당 기능의 `Editor/`에 두며, `Core`의 독립 어셈블리 경계는 유지한다.
- 파일·폴더·시트·아틀라스는 보스·캐릭터·동작·효과·배경·UI 등 함께 관리·로딩할 의미 단위를 유지한다. 파일 수를 줄이기 위해 관련 없는 이미지를 섞지 않는다.
- 기본·계승 외형은 `<소유자>/Forms/`, 부활은 `Revival/`에 둔다. 패턴별 이미지·재질·셰이더는 `<소유자>/<패턴 ID>/`에 함께 두고, 여러 패턴이 공유하면 해당 소유자의 `Shared/` 또는 작은 `Effects/` 묶음에 둔다. 새 파일은 의미 있는 동작·효과 이름과 필요한 프레임 수를 사용하며 `Variants`나 수정 버전별 보관 폴더를 만들지 않는다. 기존 Sprite 이름·논리 키와 연결된 파일명은 호환성을 위해 유지한다.
- 아트의 로딩 키는 `Arts/Resources/` 아래 상대 경로다. 플레이어 클립은 `Player/Animation/`·`Player/Animation24/`이다. 기본형과 계승형은 물리적으로 같은 `Forms` 폴더를 쓰지만 계승 로더는 기본형을 제외한다. 논리 외형명·포즈명과 저장 데이터 키는 유지한다.
- 설정 에셋은 `Data/Resources/`, 보스 Sprite 연결은 그 아래 `BossArtwork/`, 오디오 카탈로그는 `Audio/Resources/`에 둔다. 이 설정들의 기존 Resources 로딩 키는 유지한다.
- 외형 참조 atlas를 포함해 픽셀·색상 정보·슬라이스·피벗·PPU·임포트 설정·사용 목적이 호환되는 동일 이미지는 공용 원본을 공유한다. 실제 차이가 필요한 전용 이미지는 유지하고, 비슷하게 보인다는 이유만으로 합치지 않는다. 공용 이미지 변경은 모든 참조 보스에 영향을 준다.
- Sprite와 논리 이름(`poses`)은 담당 `Assets/Data/Resources/BossArtwork/Karma…BossSprites.asset`의 같은 인덱스에 연결한다. 보스 라이브러리는 자동 검색된다. 공통 라이브러리에 전용 이미지를 등록하거나 그룹/이름 조합을 중복 등록하지 않는다.
- 효과 그룹은 `RisingBossVFX`·`SwordBossVFX`·`GuardBossVFX`, 기본 외형은 `BossAppearance`, 기절은 `BossStun`, 동작 시트는 `Rise`·`Wave`·`Ward`다. 코드는 `KarmaArtwork.Sprite`·`KarmaCombatVFX.SpawnSprite`로 조회한다.
- 이동·이름 변경은 `.meta`도 함께 옮겨 GUID·Sprite ID를 보존한다. 새 복사본은 새 GUID를 쓰고 기존 `.meta`를 재생성하지 않는다. Resources 경로를 바꾸면 로더·제작 도구·검사도 함께 갱신하고 실제 로딩을 확인한다.

### 이미지 작업과 검증

1. `python3 tools/optimize-images.py --duplicates-only`로 전체 아트의 중복 후보를 찾고 기존 원본 재사용을 우선한다. 다른 인코딩의 후보는 픽셀·색상 정보도 비교한다. 통합할 파일의 참조는 6절 기준으로 확인한다.
2. 추가·변경한 의미 단위 경로만 `python3 tools/optimize-images.py --apply <경로>`로 무손실 압축한다. 전체 최적화 요청일 때만 전체를 대상으로 한다. 도구는 해제된 이미지 데이터와 나머지 청크의 동일성을 검증하고 작아진 PNG만 저장한다. 통과한 파일을 같은 작업에서 재압축·재검사하지 않는다. `--check`는 쓰기 없는 감사·CI용이다.
3. 색상·알파·해상도·프로필·Sprite 영역·피벗·PPU를 보존한다. PNG 외 형식, 손실 압축·리사이즈·아틀라스 재배치·임포트 압축·Read/Write 변경은 실제 사용처와 화질·런타임 영향을 별도 검증한다.
4. 이동·공용화·임포트 변경은 바뀐 Sprite·재질·셰이더와 Resources·논리 이름·Sprite ID 연결만 최소 확인한다. 필요하면 Unity에서 해당 연결이나 화면·전투 동작만 짧게 확인하며, 검사 범위는 7절을 따른다. 중복 유지 사유, 파일 수·용량 절감량과 결과를 보고한다.

### 제작 전 분석

- 아래 기준은 플레이어·모든 보스·적의 캐릭터 이미지, 스프라이트 애니메이션과 전투 VFX에 적용한다. 목표는 이미지 생성부터 Unity 연결·실제 플레이까지 자연스럽게 작동하는 완성된 동작이다. 담당·공통 변경 승인과 에셋 배치는 1~2절 및 위 배치 규칙을 따른다.
- 생성·수정 전에 기존 기준 이미지·저장/로딩 구조, Animator/커스텀 재생 방식, FSM·상태 전환, 패턴 실행 조건·시간·판정, VFX 생성·갱신·제거, Sprite Import·PPU·Atlas·Sorting Layer/Order, Unity 버전·URP 2D 설정을 확인한다.
- 코드에 존재하는 대기·이동·점프·돌진·일반/특수 공격·피격·기절·사망·전환과 강화·고유화·계승 상태를 빠짐없이 확인한다. 패턴별 코드 ID, 필요한 캐릭터 모션/별도 VFX, Startup·Active·Recovery 시간과 판정 구간, 이동·방향·반복 여부, 상태별 차이·종료 조건, Unity 연결 위치·구현/테스트 여부를 정리한다. 별도 문서 생성은 5절을 따른다. 없는 패턴·상태를 임의로 추가하거나 누락을 임의의 기존 모션으로 대체해 완료하지 않는다.

### 24FPS와 게임플레이 타이밍

- **모든 캐릭터와 스프라이트 기반 VFX는 제작·재생을 24FPS(프레임당 1/24초 ≈ 41.67ms)로 통일한다.** 기존 플레이어 동작은 지속 시간을 유지하며 키프레임·중간 프레임을 보완해 전환하고, 미제작 보스 동작은 처음부터 이 기준으로 제작한다. 기존 12FPS 시트를 단순히 두 배속으로 재생하지 않는다.
- 프레임 수는 `동작 시간(초) × 24`를 기준으로 정하며 무조건 24장을 만들지 않는다. 정수 프레임과 시간이 맞지 않으면 기존 게임플레이 타이밍을 우선하고, 자연스러운 범위에서 프레임 유지·재사용을 허용한다.
- 24FPS는 스프라이트 기준이다. `Application.targetFrameRate`·`Time.fixedDeltaTime`을 이에 맞춰 바꾸거나 Particle System·Shader VFX를 24FPS로 제한하지 않는다. 이동·입력·전투·물리·판정은 애니메이션 FPS와 독립시키고 프레임 드롭에도 정상 작동해야 한다.
- 기존 FSM·패턴·애니메이션 구조를 활용한다. 이미지 연결을 이유로 새 공통 프레임워크·불필요한 상태를 만들거나 공격 속도·Hitbox 구간·FSM 전환 시간을 바꾸지 않는다. 공통 애니메이션·캐릭터·판정·로더·게임 상태·VFX 시스템 변경은 1절의 승인을 따른다.

### 이미지·모션 품질과 Import

- 투명 RGBA PNG와 고해상도 원본을 사용하고, Unity 최종 에셋은 실제 표시 크기에 맞춘다. 저해상도 확대를 고해상도 제작으로 간주하지 않는다. 원본과 최종 사용본을 구분하되 불필요한 중복은 남기지 않는다.
- 참조 우선순위는 **승인된 캐릭터 기준 이미지 → 동일 캐릭터의 기존 동작·계승 이미지 → 프로젝트 공통 그림체 → 외부 동작·연출 참고**다. 기준을 확인하지 않고 재디자인하거나 외부 캐릭터를 복제하지 않는다. 결과가 기준과 다르면 기존 이미지를 임의로 바꾸지 않는다.
- 기준 외형 확정 → 시작·준비·정점·복귀 키프레임 → 중간 프레임 → 연결·24FPS 재생 순으로 제작한다. 일괄 생성의 품질이 부족하면 정상 키프레임을 참조해 개별 프레임을 제작한다. 얼굴·머리/투구·의상/갑옷·무기·비율·색상·명암·외곽선·실루엣과 상태별 고유 특징을 프레임 간 및 캐릭터 간 공통 그림체에 맞춰 유지한다.
- 실제 패턴에 맞춰 Startup → Active → Recovery를 구성하되 즉발 등 기존 설계를 우선한다. 관절·무기 궤적·시선·공중 흐름과 이동/공격 연결, 반복의 끝/시작이 자연스러워야 한다. Pivot·크기·정렬을 일정하게 유지하고 실제 이동·넉백을 이미지에 중복 반영하거나 충돌 위치를 바꾸지 않는다.
- Sprite Sheet는 동일 셀 크기로 왼쪽→오른쪽, 위→아래 순서로 배치하고 개별 프레임 순서와 맞춘다. 신체·무기가 잘리지 않는 범위에서 불필요한 여백을 줄인다. 파일명은 캐릭터·동작·상태를 식별하고 프레임 번호 자릿수를 통일한다. 캐릭터 애니메이션과 VFX는 구분 관리하되 기존 폴더 체계를 따른다.
- 기존 기준에 맞는 Single/Multiple·PPU·Pivot·Filter Mode·Atlas 참조·Sorting Layer/Order를 적용한다. 임포트·압축 후 선명도·알파·슬라이스와 연결을 확인한다. 메모리·로딩·동시 VFX 오브젝트 비용을 점검하고 반복 효과는 재사용한다. 최적화로 프레임 순서·참조·시각 품질을 훼손하지 않는다.
- 외형 변화·신체 왜곡·해상도 부족·위치/크기 흔들림·끊김·잘림·배경 잔존·불필요한 잔상·그림체 불일치는 최종 에셋으로 사용하지 않는다. 문제 프레임과 원인을 식별해 기준 이미지·정상 키프레임으로 수정하고, 연속성이 해결되지 않으면 동작을 재구성한 뒤 24FPS·Unity 재검증한다. 해결하지 못한 항목은 미완성으로 명시한다.

### VFX 연결과 완료 기준

- 캐릭터와 VFX는 별도로 제작·관리하고 기존 코드에 필요한 궤적·투사체·잔상·상승/낙하·착지·방어막/파편·패링·피격·지면/범위·고유화/계승 효과만 만든다. 모든 패턴에 모든 효과를 강제하지 않는다.
- 전조와 실제 공격 효과를 구분하고 위치·방향·크기·발생/종료를 실제 판정·투사체·충돌 지점·방어 상태에 맞춘다. 피격 효과는 실제 피격에만 표시하고 패링 성공/실패를 구별한다. 위험 방향·범위를 명확히 전달하며 캐릭터를 과도하게 가리거나 판정 종료 뒤 잔여 효과로 피해 범위를 오해하게 하지 않는다.
- 해당 제작·전환 범위의 **모든 동작·패턴·강화/고유화/계승 상태**를 Unity에서 실행한다. 24FPS·프레임 순서·반복·전환·좌우 반전·외형/위치 연속성, 모션/VFX/판정 동기화·중단/피격/패링/사망, 전조 가독성·시야·프레임 드롭 및 다수 VFX 상황의 성능·메모리를 변경 전후로 확인한다. 플레이어 전환은 모든 플레이어 동작을 재검증한다. 무관한 보스 전체 회귀는 7절을 따른다.
- 이미지·시트 제작이나 등록만으로 완료하지 않는다. 필요한 에셋·Import·기존 시스템/패턴/상태 연결, 실제 플레이·품질·게임플레이 보존·성능 검증과 결과 영상까지 갖춰야 완료다. 보고에는 **대상/패턴, 생성·수정 에셋/파일, Unity 연결 위치·코드 변경, 패턴별 검증·품질/성능 결과, 미완성/미검증 항목, 플레이 영상·브랜치/커밋·PR**을 간결하게 적는다. 영상 등 최종 결과물은 임시 검증 캡처와 구분하고 6절에 따라 관리한다.

## 4. 협업과 충돌

- 승인받은 공통 변경은 한 명이 맡아 작은 별도 PR로 분리한다. 특히 `Core`의 공격 ID·진행 규칙, `KarmaEnemy*`·`KarmaBossBehavior`의 전투 계약, 공통 전투·플레이어·연출 변경은 영향받는 보스의 변경 동작만 최소 확인한다.
- 씬·공용 에셋·설정은 동시에 편집하지 않는다. 무관한 자동 저장·임포트 변경이나 충돌 회피만을 위한 다른 보스 수정을 섞지 않는다.
- 충돌 시 양쪽 의도를 확인한다. `ours`/`theirs`로 파일 전체를 덮어쓰거나 타인 브랜치를 강제 push하지 않는다.

## 5. 문서

- 정책·작업 절차는 이 문서 한 곳에만 쓴다. `AGENTS.md`는 진입 링크만 유지하고 규칙 본문을 다른 AI 파일에 복사하지 않는다.
- **문서 생성 금지:** 사용자가 명시적으로 요청하지 않은 README·설계서·작업 보고서·날짜별 기록·검증 보고서·중복 문서를 새로 만들지 않는다. 필요한 정책은 이 문서에만 추가하고, 기존 문서로 충분하면 새 문서를 만들지 않는다.
- **도구 생성 금지:** 일회성 스크립트·복사본·이름 뒤에 숫자가 붙은 중복 도구를 만들지 않는다. 기존 도구를 재사용하고, 작업에 필요 없어진 도구는 참조를 확인한 뒤 삭제한다.
- `STRUCTURE.MD`는 현재 파일·폴더 트리만 적고 구조가 바뀔 때만 갱신한다. `.meta`·Git/IDE/Unity 캐시·검증 생성물·작업 방법·이력은 넣지 않는다.
- 이전 구조 문서·중복 규칙 문서를 남기지 않는다. 이름 변경 시 관련 링크도 수정한다.

## 6. 완료 전 정리

게임 실행·개발·빌드·검증·협업에 필요한 파일만 유지한다. 무관한 기능·실험·샘플·미사용 의존성이나 막연한 예비 파일을 추가하지 않는다. 완료 보고·커밋·PR 전에 승인 범위 안에서 아래를 한 번 수행한다.

1. 대체·삭제 후보의 코드·GUID·문자열 경로·Resources·shader include·씬·프리팹·도구 참조를 확인한다. 참조를 이전하고 관련 검증을 통과한 뒤 이전 파일과 `.meta`, 빈 폴더·폴더 `.meta`를 함께 정리한다. 이름이나 GUID 검색 하나만으로 삭제하지 않는다.
2. 자신의 임시 스크립트·백업·성공 검사 로그/캡처·Python 캐시·OS 파일은 사용 프로세스 종료 후 삭제한다. 필요한 검사 요약은 먼저 기록한다. 실패·미해결 진단 자료는 해결·재검증까지 보존한다.
3. 타인의 변경·생성물, 용도가 불분명한 파일, 유효한 구현·검사·전용 에셋·개발 중 기능은 보존한다. Git 이력·개인 설정·사용 중인 Unity 캐시를 지우거나 `git clean -fdx` 같은 일괄 삭제를 하지 않는다. 버전 백업은 Git 이력으로 관리한다.
4. `git status --short`, `git diff --check`, 잔여 참조·고아 `.meta`·구조/링크를 확인한다. 삭제 내역과 보존 후보·이유를 짧게 보고한다.

생성물은 `.gitignore`에 등록하고 임시 파일은 Assets 밖에 둔다. `Library/`·`Temp/`·`Logs/`·`UserSettings/`·`output/`·`backups/`·IDE 설정·생성 솔루션/프로젝트·캐시·비밀정보는 커밋하지 않는다. 정리는 작업 종료 절차이며 상시 감시기·예약 작업·Git hook을 설치하지 않는다.

## 7. 검증과 PR

### 검증

- Unity는 `ProjectSettings/ProjectVersion.txt` 버전을 사용한다. 무관한 Editor·패키지 업그레이드를 하지 않는다.
- **기본은 최소 검사다.** 변경한 부분의 정상 동작을 짧게 확인하는 데 필요한 검사만 수행하고, 확인되면 마무리한다. 보스 전투는 발동·명중·회복·패링·중단·사망 중 직접 영향받는 동작만 확인한다. 이미지·애니메이션·VFX 제작/전환은 3절의 해당 작업 범위 전체 검증·완료 기준을 적용한다. 문서만 바뀌면 변경 내용과 필요한 경로·링크만 확인한다.
- **전체 회귀 검사·여러 보스의 일괄 검사·장시간 반복 검사는 사용자가 명시적으로 요청한 경우에만 실행한다.** 공통 파일 변경만을 이유로 검사 범위를 자동으로 넓히지 않는다. 최소 확인에 필요하지 않은 별도 Unity 프로젝트·검증 환경도 새로 준비하지 않는다.
- 실패하면 실패한 부분만 수정·재확인한다. 새 변경이나 실패 없이 통과한 검사를 반복하지 않는다. 미실행·실패 검증을 통과로 보고하지 않고, 실제로 확인한 범위만 짧게 보고한다.
- 경계 검사: `python3 -m unittest discover -s tests -p test_boss_boundaries.py`. 공통의 보스 직접 의존·보스 간 구체 타입 참조·전용 상태 접근을 확인한다.
- Unity 실행기: `python3 tools/run-boss-playchecks.py`. 경계 검사를 먼저 실행하며, `--suite`에 아래 이름을 공백으로 나열하면 같은 복제 프로젝트에서 선택 실행한다. 실행기 자체의 기본값은 전체 실행이므로 기본적으로 인수 없이 실행하지 않는다. 필요한 부분만 직접 확인하는 것을 우선하고, suite 실행이 필요한 경우에만 해당 `--suite`를 명시한다.

| Suite | 확인 범위 |
|---|---|
| `artwork` | 배경 원본 해상도·달·카메라 범위·확대 연결 |
| `isolation` | 보스 등록·공격 연결·설정 분리·아트 참조 |

| `sw05` | 최신 SW05 비행·검 소나기·명중·완료·중단 |
| `sword` | 검기형 이동·평타·SW01~SW04 회귀 |
| `rising` | 상승형 기본·UP01~UP05 실행·자세·정리 회귀 |
| `integration` | 패링·감전·GD04 상태 전환, 리소스 실패 후 재시도, 물리 탐색 결과·할당 비교, 기존 키 설정의 재시작 복원 |

| `sword-refresh` | SW04 감전·SW05 최종 폭발 |
| `sword-scar` | SW03 80개 검·이동 병행·중단·패링·사망·후속 패턴 |
| `build` | macOS Player 빌드 |

`player24`는 선택형 Native24 원본·임포트를 복제 프로젝트에서 재생성하므로 마지막에 실행한다. 활성화 마커가 없는 저장소의 기본 애니메이션 선택은 변경하지 않는다. `--visible`은 화면이 있는 Editor에서 Play Mode 검사를 실행한다. `--work-project`는 실행기가 만든 복제 프로젝트만 재사용하며 열려 있는 Editor의 파일은 교체하지 않는다. `build`는 macOS 모듈이 설치된 환경에서 실행한다. 정적 에셋 검사는 `python3 -m unittest discover -s tests -p test_asset_integrity.py`로 GUID·메타·대소문자·Resources·셰이더 경로를 확인한다.

상승형의 모든 피격·패링 조합과 수동 플레이 전체를 보장하지 않는다. 결과는 `output/validation/`에 생성하며 보존·삭제는 6절을 따른다.
